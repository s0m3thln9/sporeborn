# Стиль C# и Unity

## Имена и оформление

| Элемент | Соглашение | Пример |
| --- | --- | --- |
| Пространство имён | `Sporeborn` и область ответственности | `Sporeborn.Gameplay.Packaging` |
| Класс, метод, свойство, событие, константа | `PascalCase` | `ShippingBox`, `TryAddMushroom`, `Capacity` |
| Интерфейс | `I` и имя контракта | `ISaveStore` |
| Аргумент, локальная переменная | `camelCase` | `remainingSeconds` |
| Закрытое поле | `_camelCase`, включая поля Inspector | `_playerCamera` |
| Булево значение | Имя, которое читается как условие | `IsClosed`, `CanShip` |

- Имена кода, файлов и ассетов пиши на английском. Используй термины механики. Например, `GrowingTray` для лотка и `ShippingBox` для продажной коробки. Избегай имён `Manager`, `Helper` и `Data` без уточнения ответственности.
- Имя основного типа совпадает с именем `.cs`-файла. Храни связанные закрытые типы рядом с владельцем. Указывай модификаторы доступа явно.
- Отступ — четыре пробела. Открывающая фигурная скобка на отдельной строке. Используй скобки у управляющих конструкций. Пиши `var`, когда тип очевиден из правой части.
- Включай единицу измерения в имя, если её нельзя понять из типа или контекста. Например, `interactionRangeMeters`, `remainingSeconds`.

## Поведение и API

- Дай классу одну понятную ответственность и минимальную поверхность API. Держи проверки и изменение состояния рядом. Извлекай общий код, когда у нескольких мест действительно одинаковые правила и причины меняться.
- Используй глаголы в именах действий. `Try...` возвращает успех или отказ с понятной причиной. Ожидаемый отказ игроку, например заполненная коробка, представляется результатом действия. Исключения обрабатывай на границе, где можно восстановиться или объяснить ошибку.
- Начинай с проверок необходимых условий. Выражай взаимоисключающие стадии одним состоянием. Используй отдельные флаги для независимых свойств.

## Исходники без комментариев

- После завершения каждой секции удаляй из её исходников все комментарии. В итоговом коде проекта запрещены строковые, блочные и XML-комментарии, включая `TODO`, `FIXME` и закомментированные фрагменты. Правило распространяется на тесты и скрипты проекта.
- Выражай намерение через имена, структуру методов и явные проверки. Причины решений и ограничения Unity документируй в Markdown.
- Перед коммитом просмотри итоговые версии изменённых исходников и удали оставшиеся комментарии и временную отладочную печать.

## Код сцены

- Используй `[SerializeField] private` для зависимостей и параметров Inspector. Проверяй обязательные ссылки при сборке компонента или инициализации, чтобы ошибка указывала на объект и поле.
- Кэшируй часто используемые ссылки. Используй `Awake` для локальной настройки, а подписки оформляй симметрично в `OnEnable` и `OnDisable`, когда они действуют только для активного компонента.
- Обрабатывай ввод и наведение в обычном кадре. Изменения физического движения выполняй в соответствии с физическим циклом. Используй `Update` только для действительно непрерывной работы. Для редких изменений подходят события или явные вызовы.
- Учитывай ссылки сцены при переименовании сериализованных полей. Используй `[FormerlySerializedAs]`, если значение уже задано в ассетах, и проверь сцены и префабы после изменения.
- Оптимизируй измеренные проблемы. В коде, который выполняется каждый кадр, избегай повторного поиска объектов по сцене и лишних выделений памяти, если можно сохранить ссылку или результат.
